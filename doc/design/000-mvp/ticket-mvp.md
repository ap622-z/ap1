# Ticket — MVP 开发票据

由 `doc/design/000-mvp/spec-mvp.md`（27 条用户故事）与 `doc/design/000-mvp/plan-mvp.md` 拆出的 13 张 **tracer-bullet 票据**。领域语义以根 `CONTEXT.md` 为准（Scope / Repository / Worker / Mailbox / Outbox）；表结构以 `doc/constitution/database-schema.md` 为准；技术选型以 `doc/constitution/tech-stack.md` 为准。

**唯一偶像定位**：系统为一位偶像设计，全链路无偶像维度、无多偶像演进（见 spec Implementation Decisions）。所有票据皆在此前提下编写。

## 使用说明

- **编号 = 依赖序**：票据以 01→13 编号，任何票据的「Blocked by」编号都小于自身，可直接从上到下顺序执行。
- **切片性质**：除 01/02 为使能型基础（数据地基 / 知识摄入，为后续提供结构与数据）外，其余均为垂直切片——每条切开一条完整通路（数据 / worker / agent / 能力 / 接口 / 前端 / 端到端测试）。
- **测试接缝**：按 spec Testing Decisions，验收以**端到端外部行为**为准，不面向内部实现；组件以 trace / 日志（带 Scope）作为唯一内部可见面。验收中的「端到端验证」均指从用户可见入口驱动。
- **状态**：全部 `ready-for-agent`——阻塞全清即可开始。

# 01 — 环境骨架与数据地基

**What to build:** 一个可一键起底的开发环境：Docker 编排 MySQL / qdrant / redis 三个中间件，Python 项目（uv 管理）能启动承载 web 入口 + Worker + Agent 单例的单进程 FastAPI 服务，六张业务表结构可幂等应用到 MySQL，qdrant 集合就绪。后续一切票据都在这片地基上生长。

**Blocked by:** None — 可立即开始。

**Status:** ready-for-agent

- [ ] `docker compose up` 一条命令拉起 mysql / qdrant / redis 三个中间件，且服务健康可连。
- [ ] uv 项目可安装依赖并启动单进程 FastAPI 应用（web + worker + agent 单例骨架齐备）。
- [ ] **App 容器化打包**：提供 Dockerfile，项目镜像可构建并运行同款单进程服务；`docker compose` 一处拉起「服务 + 中间件」，符合全容器化约定。
- [ ] redis 本轮仅拉起、无业务消费者（演进接缝——令牌→会话缓存与每用户限流于后续落地）；`/ready` 仍须确认其连通，但不作为业务事实依赖。
- [ ] 六张表（users / sessions / session_messages / idol_infos / songs / idol_lyrics）结构按 schema 全量落地，重跑不报错（幂等迁移）。
- [ ] **Repository 单一数据门面骨架建立**：方法签名强制携带 Scope（worker 面 / agent 面两组预留），作为全系统唯一的落库 / 读取入口，后续一切数据访问都经它——本票及后续不出现绕过门面的裸访问（含 SQL 直连 / 直接调用 driver）。
- [ ] 应用级 `env` 隔离生效：开发 / 生产各自指向独立数据库实例，不落表列。
- [ ] 存在一个健康检查入口，可确认服务与三个中间件的连通状态。
- [ ] 一个「进程启动即完成、Scope 携带在每条日志」的观测基线已建立（日志带 env）。

**交付的用户故事:** 无（使能型）。为 02–13 提供结构与进程底座。

# 02 — 偶像知识摄入

**What to build:** 把 `doc/asset/` 下三份素材（偶像信息 720 条、歌词、歌曲介绍）摄入为 idol_infos / songs / idol_lyrics 三表记录并生成对应 qdrant 向量。歌词 md 与歌曲介绍 md 歌目有出入，以 `song_title` 归并；无歌词正文的歌保留歌曲行。重复运行幂等，不产生重复行与重复向量。

**Blocked by:** 01

**Status:** ready-for-agent

- [ ] 运行摄入脚本后，idol_infos 得到全部 720 条、songs 得到素材归并后的完整歌目（含无歌词正文的歌）、idol_lyrics 按段归属到对应歌曲。
- [ ] 两素材歌目出入按 `song_title` 归并正确：同名异写（如空格差异）收敛到同一首，缺失的一侧不丢曲目。
- [ ] 歌词按原文段落切分为段行，每段 `seg_no` 自 1 递增、曲内唯一。
- [ ] 每条知识 / 每段歌词 / 每首 intro 均落 qdrant 向量，`vector_synced` 置 1；同 id 写入幂等。
- [ ] 重复运行摄入：无重复行、无重复向量、数据行数与首次一致（幂等可对账）。
- [ ] 某条更新正文后重摄，`content_hash` 变化、向量随之更新；被标记下架的行对应向量被移除。
- [ ] 摄入失败具备清扫路径：残留 `vector_synced=0` 的行可被补写收敛。

**交付的用户故事:** 23、24（知识录入与不引用过期内容的前提是知识已入向量库）。

# 03 — 身份与会话

**What to build:** 注册即得「唯一昵称 + 一次性登录令牌」，库中只存令牌哈希；此后每个请求经令牌校验重建出该用户**唯一**的那条会话并构造身份层 Scope（`env / user_id / session_id`）。一用户一会话由 sessions 表唯一键从结构上保证，不存在开启第二条会话的途径。

**Blocked by:** 01

**Status:** ready-for-agent

- [ ] 注册接口返回唯一昵称与明文令牌（仅此一次），库中仅存 SHA-256 哈希。
- [ ] 携带令牌的请求通过鉴权并定位到该用户唯一会话；无令牌 / 错令牌 / 停用用户被拒。
- [ ] 会话惰性创建：首次持令牌访问时创建，之后恒复用同一条；sessions 层面不存在该用户第二条会话（端到端验证）。
- [ ] 鉴权即把请求绑定到该用户唯一会话（Scope 身份层构建完成），后续消息路径无法脱离此会话。
- [ ] 令牌明文在任何日志 / 响应体 / 数据库之外不落盘。

**交付的用户故事:** 1、2、3、4（UI 无第二会话入口由 05 承接）、5。

# 04 — 最小对话闭环

**What to build:** 一条完整通路的最小版：用户发一条文字消息 → 落库（含幂等键与估算 token）→ Worker 驱动 Agent 单例做单次模型调用（接 DeepSeek API，端点 / 密钥经环境注入、不进代码与文档）产出整包回复 → 回复落库并随同一次 HTTP 响应返回；另有历史读取接口。此票据刻意先以「无工具的最小 Agent」打通闭环，能力在 08–12 逐步加厚。

**Blocked by:** 03

**Status:** ready-for-agent

- [ ] 端到端：持令牌发一条消息，响应体即含该条消息对应的完整文本回复（非流式、一次 HTTP 响应返回）。
- [ ] 该用户消息与 agent 回复按序落库，回复行以 `origin_message_id` 关联发起它的用户消息。
- [ ] 历史读取接口按会话返回该会话全部消息（刷新 / 重开可恢复）。
- [ ] 历史读取支持按序拉取（游标 / 分页形态）——MVP 会话消息可达数百轮，前端长历史滚动时无需一次全量加载。用于「刷新恢复」的主通道仍为接口；对话交付本身不走它。
- [ ] 消息 `status` 流转到 `replied`，`seq` 顺序正确；`client_message_id`、`token_count` 随 user 消息行落库。
- [ ] 错误统一为结构化返回（未授权 / 会话越界 / 处理失败等 MVP 必要分支），且响应 / 日志携带 Scope。
- [ ] 本次执行产生带 Scope 的 trace 与日志，可在日志中把一条请求从入口串联到回复（可回放，不设内部测试接口）。

**交付的用户故事:** 6、7、10（历史读取接口侧）、26（trace 雏形）。25 的「按 Scope 重建上下文」落点在 12、隔离收口在 13。

# 05 — 网页对话 UI

**What to build:** 一个微信式单会话网页：首次进入先注册 / 登录获得自己的身份凭据（昵称 + 令牌），此后以该身份进入唯一的与偶像对话窗口。气泡式收发消息、可发送、等待完整回复；刷新 / 重开页面后历史照旧。结构上不存在「新建第二条会话」的控件或入口。

**Blocked by:** 04

**Status:** ready-for-agent

- [ ] 提供身份入口：新用户注册获得唯一昵称 + 令牌（令牌仅本次展示，本地保存），老用户凭昵称 + 令牌登录；凭据后续自动携带。
- [ ] 登录成功后页面仅提供一个与偶像的对话窗口，无任何开启第二会话的途径。
- [ ] 可输入并发送文字，偶像回复以完整气泡呈现，多轮对话纵向滚动可读。
- [ ] 刷新 / 重新打开页面后完整历史恢复（走历史读取接口）。
- [ ] 发送中的消息有可见状态（等待中），不会因发送操作丢字；前端为每条消息生成幂等键并随发送携带——网络失败重试沿用同键，为后端「不重复回复」提供前提（去重由 07 端到端保证）。
- [ ] 前端鉴权走与后端一致的令牌；未登录不可进入会话页。

**交付的用户故事:** 1、2（前端身份入口侧）、4（结构上无第二会话入口由本票补全）、6、7、9（前端幂等键前提）、10。

# 06 — 同会话串行与消息生命周期

**What to build:** 引入 Mailbox（进程内、按会话键控）：同会话消息逐条按到达顺序处理、至多一条在途，永不交错；跨会话仍并行。同时落地消息生命周期 `received → processing → replied`，以及「工具记录 + 回复 + 置 replied」同一事务原子落库的 worker 收尾动作。

**Blocked by:** 04

**Status:** ready-for-agent

- [ ] 同一会话短时间内连发多条：逐条按序处理，每条各得恰好一次回复，回复与消息顺序一致、不交错。
- [ ] 不同会话可同时处理（跨会话并行），互不阻塞。
- [ ] 长回复期间新消息排队等待，处理完成后按序继续，不丢失。
- [ ] 消息落库即 `received`，进入处理即 `processing`，完成即 `replied`；生命周期对历史读取可见。
- [ ] 工具记录 + agent 回复 + 该用户消息置 `replied` 在同一批事务内提交；任一步失败则整体回滚、消息停在可见状态（processing）。
- [ ] 端到端验证：处理中该消息若失败，消息不消失、仍可见可重发。

**交付的用户故事:** 8、11（排队按序）、27 的前提。

# 07 — 幂等与失败重发

**What to build:** 以 `client_message_id` 为幂等键：同一会话重发同键的消息命中已有结果并复用，绝不触发第二次 Agent 执行；跨会话 / 不同会话同键互不影响。命中即复用已有结果是 MVP 对「幂等冲突返回体」的默认语义（plan §5）。中途失败后凭同键重发即可恢复，不静默丢失、不重复回复。

**Blocked by:** 06

**Status:** ready-for-agent

- [ ] 同会话同 `client_message_id` 重发两次：第二次不产生第二次 Agent 执行，返回与首次一致的结果（端到端验证回复不重复）。
- [ ] 同键重发时若首次结果已就绪：直接复用（plan 默认语义）；若尚在 processing：按序排队，等锁后命中既有结果，不重复跑。
- [ ] 不同用户 / 不同会话即使使用相同 `client_message_id` 也互不干扰（作用域限定在会话内）。
- [ ] 处理中途失败后凭同键重发：消息不静默丢失、最终得到恰一次回复。
- [ ] 同键不同内容投递的冲突被明确处理为幂等命中，不重复执行、不产生歧义回复。

**交付的用户故事:** 8、9、27。

# 08 — 自定义 Agent 执行循环与能力层骨架

**What to build:** 用自写主循环替换 04 的最小单次调用：每步「调模型 → 输出二选一（文本即结束 / 工具调用即经能力层执行并把结果写回当步上下文 → 下一步）」。一次回复 = 一次 run，run 内每轮模型 + 工具 = 一个 step，run/step 生成并写入带完整 Scope 的日志。能力层登记 tool / skill / mcp 三种形态（本票先立骨架与护栏，具体能力由 09/10/11 填充）。护栏：单 run 最大步数、每步 token 预算，超限体面收尾不中断会话。

**Blocked by:** 04

**Status:** ready-for-agent

- [ ] 纯文本场景：模型一次调用即产回复结束，行为与 04 兼容。
- [ ] 工具场景：模型输出工具调用 → 能力层执行 → 结果写回 → 模型据结果续步，直至文本回复结束。
- [ ] 单步工具失败不中止 run：结果标记失败交回模型重新决策（工具兜底逻辑）。
- [ ] 触达单 run 最大步数或每步 token 上限：强制收尾，仍返回体面回复、会话不中断（对能力不可用的兜底前提）。
- [ ] 一次回复对应一次 run，其内部模型 / 工具轮次对应 step；run/step 均带完整 Scope 写入日志，可跨组件串联回放。
- [ ] 能力层已能登记三形态（tool / skill / mcp），供 09 / 10 / 11 各自填充一个实例。

**交付的用户故事:** 22、26（run/step 全量）。25 的「按 Scope 重建上下文」落点在 12、隔离收口在 13。

# 09 — 知识检索 tool（RAG 读路径）

**What to build:** 打通第一个 tool：**偶像信息检索**。Agent 遇到偶像背景 / 经历 / 作品 / 歌曲等提问时，经能力层调用检索：qdrant 向量召回候选 id → 回 MySQL 按 id 校验（行存在、`content_hash` 匹配、`status` 上架）→ 只把校验通过的内容交给模型作答。用户侧效果：问偶像与歌曲相关问题得到有据可查的回答，且不引用已删除 / 过期的知识。

**Blocked by:** 02, 06, 08

**Status:** ready-for-agent

- [ ] 端到端：问偶像背景 / 经历 / 作品类问题，回复基于检索到的真实资料内容，而非凭空编造。
- [ ] 问歌曲 / 歌词相关问题，能依歌词段或歌曲介绍内容回应。
- [ ] 知识读路径的「回查校验」生效：下架 / 哈希不匹配 / 行缺失的向量不被召回为用户可见内容。
- [ ] 检索无命中：Agent 诚实说明、不编造，会话不断。
- [ ] 一次检索作为 tool 记录与该消息同一事务落库，可追溯该回复引用了哪些条目。

**交付的用户故事:** 18、19、24（读路径侧）。

# 10 — 提问 skill（含糊澄清）

**What to build:** 打通第一个 skill：**提问**（行为指导而非可调用函数）。当用户表述含糊、且缺失信息可能影响会话后续理解与判断时，把「先巧妙反问澄清再继续」的指导注入当次 prompt，引导 Agent 反问而非自行假设。MVP 用轻量规则（信息缺失 / 含糊信号）判定是否注入。

**Blocked by:** 08

**Status:** ready-for-agent

- [ ] 端到端：用户给出含糊 / 关键信息缺失的表述时，Agent 先反问澄清，不自行假设关键信息。
- [ ] 表述清楚时不被误触发，正常作答不受干扰。
- [ ] 澄清回合与主对话同处一个会话、正常落库，语义连贯。
- [ ] 命中 / 未命中提问规则都有迹可查（日志可见该 skill 是否注入当次 prompt）。

**交付的用户故事:** 20。

# 11 — 联网搜索 mcp

**What to build:** 打通第一个 mcp：**联网搜索**。在能力层把外部搜索服务（如 Tavily）登记为可调用工具，与本地 tool 同接口形态。模型判断问题需要实时 / 外部信息时调用之，并把搜索结果用于作答。搜索失败走护栏兜底，不中断会话。

**Blocked by:** 08

**Status:** ready-for-agent

- [ ] 端到端：提出需要实时 / 外部信息的问题时，Agent 触发联网搜索并基于搜索结果回答，回复提及信息来自联网检索。
- [ ] 搜索服务不可用或失败：Agent 体面说明、不编造、会话不断（护栏兜底生效）。
- [ ] 联网搜索与本地 tool 在能力层以同一接口形态登记，可被同一执行循环调度。
- [ ] 搜索调用作为 tool 记录与该消息同一事务落库。
- [ ] 搜索凭据经环境注入，不落库、不进日志。

**交付的用户故事:** 21、22。

# 12 — 上下文窗口与压缩

**What to build:** Agent 内部按 Scope 组装上下文窗口 = Summary（压缩历史）+ `summary_seq` 边界之后全部轮次（含每轮工具记录）。写入方估算 `token_count`；组装时窗口总 token 超预算即触发一次压缩：把「最近 10 轮之前」的轮次经 LLM 重写并入 Summary，更新 `sessions.summary_text / summary_tokens / summary_seq`。**最近 10 轮永不压缩**，始终原文在窗。被压缩的旧消息行仍留库（历史完整），只是不再进窗口。Summary 属会话内记忆，受 Scope 隔离。

**Blocked by:** 06

**Status:** ready-for-agent

- [ ] 端到端：会话聊得很长、接近模型上下文限制时仍能继续，不被截断。
- [ ] 基础记忆：未触发压缩时，Agent 也能回指本会话较早轮次（窗口含 `summary_seq` 边界后全部轮次），对话连贯、不前后矛盾。
- [ ] 窗口超预算触发一次压缩：较旧轮次被并入 Summary 持久化，随后对话语义连贯、不前后矛盾。
- [ ] 最近 10 轮始终以原文留在窗口；压缩后窗口 = 新 Summary + 最近 10 轮。
- [ ] 压缩动作在会话串行边界内完成（Mailbox 保障），并发下不产生摘要写冲突。
- [ ] Summary 只属于本会话：另一用户 / 另一会话无法读到、无法被卷入（端到端隔离验证）。
- [ ] 被并入 Summary 的旧消息行仍在库中可查（历史完整性），只是不再进入上下文。

**交付的用户故事:** 12、13、14、25（每次执行按 Scope 重建上下文，无跨用户状态）。

# 13 — 隔离加固、体面兜底与全量端到端验证

**What to build:** 最后一张收口票据。数据隔离的**系统级兜底**与规格关键场景的**全量端到端验收**：Repository 面不存在无 Scope 的裸访问，任何越界引用他人会话 / 身份的请求在数据层被拒；能力不可用 / 处理中途失败时回复体面、消息不丢不重。规格列出的关键测试场景在此整体跑绿。

**Blocked by:** 07, 09, 10, 11, 12（各能力与隔离前提就绪后收口）

**Status:** ready-for-agent

- [ ] 端到端：两用户同时在线、同时发消息，彼此看不到对方任何消息 / Summary / 回复（含压缩摘要），无串扰。
- [ ] 试图引用他人会话或身份的请求被拒（数据层兜底，非仅靠上层自觉）。
- [ ] Repository 侧审计：不存在不携带 Scope 的裸访问路径（代码审查结论）。
- [ ] 能力不可用或处理中途失败：Agent 体面回应、会话不中断；凭同键重发不丢不重（与 07 语义一致）。
- [ ] 用户链路数据永不写入向量库（用户消息 / 回复 / 摘要只进 MySQL）——知识链路为唯一双写来源。
- [ ] 规格关键测试场景全绿：并发隔离 / 同会话按序恰一次 / 同键幂等 / 超阈值压缩后连贯 / 检索有据 / 含糊反问 / 联网搜索 / 知识更新后不回引过期内容 / 失败重发不丢不重。

**交付的用户故事:** 15、16、17、22、27、25 隔离侧（全量收口）。
