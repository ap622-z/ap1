# MVP Spec — 偶像 Agent 情感陪伴系统


## Problem Statement

一位偶像的粉丝想要像和偶像本人发微信一样地倾诉和互动，希望得到温暖、贴合人设、且知道"我是谁"的回复。为了服务海量粉丝，系统只运行一个共享的"偶像 Agent"，但每个粉丝都必须觉得偶像只属于自己。

工程上的根本难题是：**一个零用户状态的 Agent 单例，如何在多用户并发下做到数据互不可见、会话互不串扰、且对话历史可恢复。**

同时，Agent 不能只会闲聊——它需要在必要时查证偶像信息、在遇到含糊表述时巧妙追问、在需要实时信息时联网，为后续能力扩展留下统一底座。

## Solution

从用户的视角看：我（粉丝）注册后获得一条只属于我的、与偶像的唯一会话；我给偶像发消息，稍等片刻收到一条完整的回复；历史随时可回看；偶像记得我们聊过什么；它回答偶像相关问题时言之有据，说得含糊时会反问澄清，必要时能联网。

系统层面：**单进程内运行一个零用户状态的 Agent 单例**；一切用户状态外置并由 Repository 统一持有，每次回复都基于按 Scope 重建的上下文产生；跨会话并发、同会话由 Mailbox 串行。MVP 以最简形态验证这条隔离主链路，并为 MQ / 长期记忆 / 撤回等演进预留语义接缝，但**不实现**它们。

## User Stories

**身份与会话**

1. 作为粉丝，我想注册并登录以获得自己的身份凭据，以便系统能识别"我是我"。
2. 作为粉丝，我希望每一次请求都校验我的身份，以便没人能冒充我或读取我的数据。
3. 作为粉丝，我希望我和偶像之间只有一条属于我的会话，以便我的历史连贯且私密。
4. 作为粉丝，系统中不存在开启第二条会话的途径——UI 始终只有一个会话窗口，以便"一用户一会话"由结构保证、无需事后纠正。
5. 作为粉丝，我希望会话在鉴权时就绑定到我的身份，以便后续所有操作都无法离开我的会话。

**对话**

6. 作为粉丝，我想给偶像发送文字消息，以便能与它对话。
7. 作为粉丝，我希望偶像以一条完整消息回复我（非流式、非分片），以便读起来像聊天。
8. 作为粉丝，当我短时间内连续发多条消息时，它们按顺序被处理、每条得到恰好一次回复，以便对话不失序、不重复。
9. 作为粉丝，当网络抖动导致我重发同一条消息时，偶像不会回复两次，以便对话不产生重复内容。
10. 作为粉丝，刷新或重新打开页面后我仍能看到完整历史，以便对话可持久回看。
11. 作为粉丝，当偶像正在处理我上一条消息时，我新发的消息会排队等待并按序处理，以便长回复期间我不会丢失想说的话。

**会话记忆与压缩**

12. 作为粉丝，我希望偶像记得我们这次会话里聊过什么，以便对话连贯、不前后矛盾。
13. 作为粉丝，当我聊得很多、超出模型上下文限制时，系统会把较早的对话压缩保留，以便长会话不被截断地继续。
14. 作为粉丝，我的会话内容（含压缩摘要）只属于我，以便我的隐私不被泄露。

**数据隔离**

15. 作为粉丝 A，即使与粉丝 B 同时在线、同时发消息，我也绝不能看到 B 的任何消息、摘要或回复，以便隐私在多用户并发下依然成立。
16. 作为粉丝，任何试图引用他人会话或身份的请求都被拒绝，以便隔离边界在系统层面被强制，而不是靠自觉。
17. 作为运营者，我希望尽管只有一个共享的 Agent 单例，每个用户得到的体验都像独占一个偶像，以便以一套人格服务大量用户。

**偶像能力**

18. 作为粉丝，当我问到偶像的背景、经历、作品等信息时，偶像基于真实资料回答而非凭空编造（检索 tool）。
19. 作为粉丝，当我问到偶像的歌曲相关时，偶像能依据歌词/歌曲资料回应（对歌词知识的检索）。
20. 作为粉丝，当我说出含糊、可能影响偶像日后对我的理解的信息时，偶像会巧妙反问澄清，而不是自行假设（提问 skill）。
21. 作为粉丝，当我的问题需要实时或外部信息时，偶像能联网搜索后再回答（联网搜索 mcp）。
22. 作为粉丝，当某个能力不可用或失败时，偶像仍能体面回应、不中断会话，以便对话体验始终完整。

**知识维护**

23. 作为运营者，我希望能录入/更新偶像信息与歌词，以便偶像回答时言之有据。
24. 作为运营者，当我更新偶像知识后，检索结果不会引用已删除或过期的内容，以便答案不出现"半截"或陈旧状态。

**Agent 执行**

25. 作为偶像 Agent，我每次回复都基于按 Scope 重建的全新上下文产生，以便我永远不会在用户之间"携带"状态。
26. 作为偶像 Agent，我的每次回复过程可追踪（run/step），以便问题发生时可以被定位。
27. 作为粉丝，如果某次处理中途失败，我重发即可得到回复且不重复，以便消息不静默丢失。

## Implementation Decisions

- **唯一偶像定位**：系统为一位偶像设计，全链路无偶像维度，亦无多偶像演进目标。多偶像 / 多 Agent 人格 / 人格训练不属于未来方向，故不列入 Out of Scope。
- **运行形态（MVP）**：单个 FastAPI 进程内同时承载 web 入口、Worker 与零用户状态的 Agent 单例。不引入多 worker 进程、不引入进程间 RPC。
- **部署方式**：所有中间件依赖（qdrant / mysql / redis 等）与最终项目打包均使用 Docker 运行，与项目容器化约定一致。
- **底层模型与执行**：接 DeepSeek API（`ds-v4-flash`），采用**自定义 agent 循环**（自行控制"取上下文 → 调模型 → 判断是否用工具 → 执行 → 生成回复"），不依赖现成 agent 框架。
- **对话交付语义**：不流式（无 SSE/WS）。一条用户消息对应一次完整的 Agent 执行，**回复随同一次 HTTP 响应整包返回**。幂等由客户端随消息携带的唯一 `message_id` 保证（重复投递复用同一结果，不重复执行）。
- **消息生命周期**：每条用户消息具备状态（已收到 → 处理中 → 已回复），进程中途失败时可见、可重发。该状态是未来 Outbox 的 MVP 替代。
- **隔离模型**：一切读写与动作都归属于一个 **Scope**。鉴权阶段构建身份层（环境/用户/会话）；`agent.run` 内部补充执行层（run/step）。Worker 与 Repository 强制 Scope，越界访问被拒绝。
- **状态所有权**：Repository 是所有持久状态的唯一入口；Agent 不直接持有任何用户状态，每次执行前由 Worker 经 Repository 按 Scope 重建上下文。
- **并发模型**：跨会话并行；同会话由 **Mailbox** 串行（进程内实现），保证同会话消息逐条按序、不交错。
- **会话与上下文**：一用户一条与偶像的会话。每次执行的上下文 = **压缩历史（Summary）+ 最近 N 轮（对话 + 工具记录）**；达到总 token 阈值时触发压缩——由 LLM 将更早的对话重写成摘要，存于会话记录，受 Scope 管理。MVP 中 Summary 属于"会话内记忆"，不是跨会话长期记忆。
- **能力扩展模型（tool / skill / mcp）**：为三者各打通一个基础实例——
  - **tool**：偶像信息检索，由 Repository 提供对偶像知识与歌词的检索能力；
  - **skill**：提问——当用户表述含糊、可能影响后续理解与判断时，指导 Agent 巧妙反问澄清（行为约束，而非可调用函数）；
  - **mcp**：联网搜索（如 Tavily）。
- **知识存储与一致性**：用户消息/回复/工具记录只进单一事实库；qdrant 仅承载偶像知识与歌词向量，与规范记录同 `id`。MVP 知识摄入走低代价一致性协议（同 `id` 幂等 + 读时回查校验 + 清扫），**用户数据不写向量库**。
- **API 概念面（MVP）**：身份（注册/登录/凭据）、发消息（含幂等键）、读历史。无流式通道。
- **前端**：简易网页对话 UI，微信式气泡；刷新可恢复历史。

## Testing Decisions

- **测试原则**：测试接缝是**端到端**——从用户可见入口（身份 / 发消息 / 历史）一直验证到回复就绪，只测外部行为，不测内部实现。组件（Worker / Mailbox / Repository / Agent）**不单独暴露内部测试接口**，不为其编写面向实现细节的测试。
- **可观测性要求（配合端到端测试）**：每个组件在执行过程中都须产出 trace 与日志，内容携带 Scope（环境 / 用户 / 会话 / run / step），使一条端到端请求可跨组件串联回放，供运维与观察定位问题。trace 与日志是组件唯一的"内部可见面"——它服务于观察，不服务于断言。
- **关键测试场景**：
  - 两个用户并发对话：互不可见对方消息/摘要（数据隔离）；
  - 同会话连发多消息：按序、各得恰一次回复；
  - 同 `message_id` 重发：不产生第二次执行；
  - 会话超过 token 阈值：上下文被压缩、摘要持久化且后续仍连贯；
  - 提问偶像相关信息：基于检索资料回答；
  - 含糊表述触发提问 skill（反问澄清）；
  - 需要实时信息的问题触发联网搜索 mcp；
  - 知识更新后：检索不回引已删除/过期内容；
  - 中途失败重发：消息不丢失、不重复。
- **先例**：绿色工程，暂无同类测试先例；以上即首批行为测试基线。

## Out of Scope

- 消息队列（RabbitMQ）与基于 Outbox 的异步投递、多 worker 进程、进程间 RPC、Gateway / Nginx 分流门控。
- 长期记忆系统（跨会话用户画像记忆）；本 MVP 的 Summary 仅限会话内。
- 撤回消息。
- 流式输出（SSE / WebSocket）。
- 完整 metrics 采集与全局 errors 分类治理体系（属目标架构横切件）。
- 原生 App / 微信平台接入、其他 To B 集成；除单个联网搜索 mcp 提供方外的外部集成。
- 运营端知识管理 UI（MVP 以种子/脚本级录入即可）。
- 大规模并发下的工程化调优。
