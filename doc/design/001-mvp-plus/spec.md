# MVP+ Spec — 偶像 Agent 情感陪伴系统（补齐交付缺口）

> 本文件是 001-mvp-plus（下称"本版"）的需求规格，是 `000-mvp` 的**工程收口增量**。
> 产品能力规格的事实基仍是 `doc/design/000-mvp/spec-mvp.md`：凡本文件未改写的 000 用户故事，在本版继续有效。
> 领域语义以根 `CONTEXT.md` 为准；表结构以 `doc/constitution/database-schema.md` 为准。

## Problem Statement

000-mvp 在桩环境下验证了三条主链路（数据隔离、会话串行、RAG 检索），但作为一个"能上手持续使用"的系统仍存在四类缺口：

1. **从未真实运行过**：全链路只在协议桩 + 本地嵌入下通过；真实 DeepSeek chat、硅基流动嵌入、Tavily 搜索的协议与响应形态从未被验证，真实输出下的函数调用解析、向量探测、检索兼容都可能藏着未知 bug。
2. **运行基线不可靠**：三种数据库未挂卷持久化，容器一重建数据即丢，无法作为稳定开发/运行基线。
3. **结构混乱**：后端目录平铺、命名混乱，无清晰的组件边界与统一配置入口。
4. **无前门**：缺少 nginx，前后端动静未分离，后端进程既当 API 又托管静态文件。

从"我（当前开发者）"的视角看，需要一次**不新增产品功能**、只把运行底座与代码结构补到"可交付给自己持续使用"的收口。

## Solution

本版在 000 产品能力范围**不变**的前提下，做四类工程收口：

- **持久化**：三种数据库（mysql / qdrant / redis）以命名卷持久化；确立"空卷冷启动"基线契约（一次性自动建库建表 + 灌知识，此后重启不重建、不重灌、不丢数据）。
- **启动正确性**：每次启动幂等；空库首启的知识摄入是必需步骤、失败即中止启动；关键配置缺失阻止启动并给出清晰错误；运行期组件不可用进日志并严肃告警，不打断会话。
- **结构重构**：后端包 `app` 更名为 `backend`，按组件分子目录（agent / worker / repository 各自成目录），设 config 目录统一读取 env 作为全局配置；纯结构调整，不改任何对外行为与数据结构。
- **nginx 前门**：新增 nginx 容器作为唯一对外入口——`/` 提供前端静态（含 SPA 回退），`/api` 反代到后端；前端产物打进 nginx 镜像，后端不再托管静态，保持 `docker compose` 单命令启动。

本版全部围绕"真实运行可用性"收口。上线测试由我（验收人）本人执行；`## Acceptance Checklist` 是本版交付给我的定义（见下文）。

## User Stories

编号连续。演员：**我自己** = 当前开发者；**粉丝** = 000 定义的终端用户（真实 API 下行为仍须成立）。

### 运行与持久化

1. 作为我自己，我希望三种数据库（mysql / qdrant / redis）以命名卷方式运行，使容器无论 `down`/`up` 多少次，数据都保留。
2. 作为我自己，我希望把环境清到零基线后，`docker compose up` 单命令起来即自动完成建库、建表、建向量集合、灌入偶像知识，使冷启动可复现、开箱即用。
3. 作为我自己，我希望每次启动幂等：无表则建、有表不重建；知识有数据就不重复灌入；多次重启不产生任何重复副作用。
4. 作为我自己，我希望重启后之前注册的用户、会话历史、偶像知识与向量全部还在，且 app 不重新执行建表或灌入。
5. 作为我自己，我希望"清空重建"只能由我显式执行（如 `docker compose down -v` 或删卷），日常重启绝不会触发清空或重建。

### 启动正确性与配置

6. 作为我自己，我希望关键配置缺失（如嵌入 API Key / 模型未配）时启动被**显式阻止**，并给出能指出缺什么、怎么修的清晰错误，防止带病启动成一个"检索全废的假健康"系统。
7. 作为我自己，我希望空库首启时知识摄入是**必需步骤而非可选项**：失败必须中止启动并严肃告知原因，绝不继续带病运行。
8. 作为我自己，我希望在我显式选择降级（如关闭自动灌入、改用离线嵌入）时仍能启动做 UI / 本地调试——这是有意为之，不算带病。
9. 作为我自己，我希望运行期某个外部能力（模型 / 联网）瞬时不可用时不打断会话（沿用 000 兜底），但要写入日志、以严肃方式告警，而不是无声降级。
10. 作为我自己，我希望 API 密钥只经宿主 `.env` / 环境注入、永不进代码库或镜像，使交付物本身不含任何真实密钥。

### 结构重构

11. 作为我自己，我希望后端包名由 `app` 改为 `backend`，并按组件划分目录，其中 agent、worker、repository 这三个大组件各自成目录，另设 config 目录统一读取 env / `.env` 作为全局统一配置，使结构清晰、职责可循。
12. 作为我自己，我希望这次重构是**纯结构调整**——不改任何对外行为、数据表结构与接口形态，也不夹带功能改动，使重构可独立验收、风险可控。
13. 作为我自己，我希望包名与组件化之后，代码内的 import、测试、CLI 入口、容器启动命令与文档引用全部同步更新，不残留任何指向旧包名的死引用。

### nginx 前门

14. 作为我自己，我希望新增 nginx 容器作为**唯一对外入口**：`/` 由它提供前端静态（含 SPA 回退），`/api` 由它反向代理到后端，实现动静分离与端口收敛。
15. 作为我自己，我希望前端构建产物打进 nginx 镜像、后端容器不再托管静态文件，从而保持 `docker compose` 单命令启动的既有形态。
16. 作为我自己，我希望经由 nginx 从浏览器访问时，打开页面与调用 `/api` 都正常（同源、刷新/直达子路由不 404），与直连后端体验一致。
17. 作为我自己，我希望本版对外即 http 即可交付验收；https / TLS 不在本版需求内，留待后续。

### 真实运行可用（000 行为在真实 API 下成立）

18. 作为粉丝，我希望在真实模型密钥下发消息能拿到一条完整的、像聊天一样的回复（真实 chat 输出 + 函数调用解析正确），对话不因真实输出形态而断。
19. 作为粉丝，我希望问到偶像信息 / 歌曲 / 歌词时，偶像基于真实检索链路命中资料回答而非编造（真嵌入召回 → 回库校验 → 生成）。
20. 作为粉丝，我希望表述含糊时触发巧妙反问、需要实时 / 外部信息时触发联网，两者在真实 API 下依然成立。
21. 作为粉丝，我希望长会话超出预算触发压缩后仍能连贯继续（真实 LLM 下的摘要重写可用）。
22. 作为我自己，我希望 chat / embed / search 三家外部提供方适配层对**真实协议与真实响应形态**兼容——这是 000 从未验证、本版必须补齐并自测通过的部分。

## Acceptance Checklist（验收清单）

**定义**：以下是本版"可交付"给我的判定标准——**每一项都必须实现完成，且我（实现方）在提交前已对其自测正确**。标注 ⭐ 的项必须以真实密钥跑通一次真实运行方可判过。此清单属本 spec 范畴；我提交后可自行启动复核。

### 持久化 / 冷启动

- [ ] **A01 卷持久化**：三个数据库均挂载命名卷；`docker compose down` 再 `up` 后，容器内数据目录仍保留数据，不因容器重建而丢。
- [ ] **A02 空卷冷启动**：删除全部容器与卷后，`docker compose up`（含构建）单命令成功；启动自动完成 建库 → 建表 → 建向量集合 → 灌入偶像知识；打开页面与调用 `/api` 均可用。
- [ ] **A03 幂等启动**：`docker compose down`（不带 `-v`）再 `up`，启动日志无"重复建表 / 重复灌入"动作；表、用户与会话数据、知识、向量均仍在。
- [ ] **A04 显式清空**：`docker compose down -v` 后数据确被清空、回到 A02 的空基线；普通 `up`/`down` 从不触发清空或重建。
- [ ] **A05 知识持久一致**：重启后提问偶像相关知识，回答仍基于留存的知识与向量命中——不存在"app 起来了但检索全废"的假健康。

### 启动正确性 / 配置

- [ ] **A06 缺 key 阻止启动**：非降级形态下缺少嵌入 key / 模型时，进程启动被阻止，错误信息能指出缺什么、怎么修；补齐后正常启动。
- [ ] **A07 首启摄入失败中止**：空库首启遇摄入失败（如断网 / 错 key）时启动中止并给出严肃指引，绝不带病继续成一个空知识库的假健康。
- [ ] **A08 显式降级可启动**：以显式开关（关闭自动灌入 / 离线嵌入等）启动成功，日志标明当前处于降级模式，可用于本地 / UI 调试。
- [ ] **A09 密钥隔离**：git 版本库与镜像内均不含任何真实密钥；`.env` 未入库；`.env.example` 仅含占位。
- [ ] **A10 运行期故障告警**：外部能力（模型 / 联网）失效时对话不中断（000 兜底），且日志出现明确的 ERROR / 告警，而非无声降级。

### 结构重构

- [ ] **A11 重构回归**：包更名与目录组件化后，既有端到端测试全套通过——证明对外行为不变。
- [ ] **A12 无旧引用**：全仓（代码 / 测试 / CLI 入口 / 容器启动命令 / 文档）无任何指向旧包名的残留引用。
- [ ] **A13 统一配置生效**：后端经统一 config 目录读取 env / `.env` 获取全部运行参数，无散落的硬编码配置。

### nginx 前门

- [ ] **A14 nginx 动静分离**：经 nginx 打开页面正常；刷新 / 直达子路由走 SPA 回退、不 404。
- [ ] **A15 nginx 反代 `/api`**：页面内的全部 `/api` 请求经 nginx 成功到达后端（同源无 CORS、无路径丢失）。
- [ ] **A16 单一对外入口**：对外仅 nginx 一个发布端口；其余容器（mysql / qdrant / redis / 后端）端口不对公网发布——仅容器网络内或本机可达。
- [ ] **A17 后端不托管静态**：直连后端进程不再返回前端页面（属预期）；静态文件仅由 nginx 提供。

### 真实运行（⭐ 真实 key 下）

- [ ] **A18 ⭐ 真实对话**：以真实密钥发消息能拿到一条完整回复；真实 chat 输出下的函数调用解析正确并能收尾，不崩溃、不中断。
- [ ] **A19 ⭐ 真实检索**：提问偶像信息 / 歌曲 / 歌词，回答有依据（命中真实资料）；凭空编造为不通过。
- [ ] **A20 ⭐ 反问 skill**：表述含糊时触发巧妙反问澄清。
- [ ] **A21 ⭐ 联网 mcp**：需要实时 / 外部信息的问题触发真实联网搜索，并基于搜索结果回答。
- [ ] **A22 ⭐ 长会话压缩**：对话累积越过预算触发压缩；压缩后继续对话仍连贯，历史仍完整可取。

## Implementation Decisions

- **范围锁定**：本版不新增任何产品功能（nginx 属运行基建，不算产品功能）；不改表结构、不引入数据迁移。000 的全部用户故事在本版继续有效，作为回归基线。
- **数据持久化**：mysql / qdrant / redis 各挂一个**命名卷**；确立"空卷冷启动"契约——清空基线（`down -v`）后单命令启动须自动完成建库、建表、建集合、灌知识。
- **启动幂等**：沿用现有迁移形态（`CREATE TABLE IF NOT EXISTS` + 素材驱动列宽的幂等对齐），本版**不引入**版本化迁移工具或 `schema_migrations` 账本（当前无表结构变更需求；该方案留待出现首个真实 schema 变更时再讨论）。
- **知识摄入语义**：灌入判定 = 偶像知识为空；空库首启时摄入为必需步骤，失败即中止启动并给出明确指引；库已有数据时永不重灌。
- **一致性兜底**：出现"知识表有行但向量集合为空/缺失"（如仅 qdrant 卷丢失的异常）时，启动须自愈补灌或显式报错，不得静默进入坏 RAG。具体取自愈还是报错在 plan 细化。
- **启动配置校验**：运行形态（非 test、非显式降级）下，真实提供方所必需的密钥 / 模型未配置即**阻止启动**，并以可读错误列出缺失项。显式降级开关（如关闭自动灌入、离线嵌入）允许启动，属有意为之。
- **运行期降级语义**：模型 / 联网调用失败沿用 000 的"体面兜底、不中断会话"；但必须以 ERROR 级结构化日志 + 明确告警记录，不得无声降级。
- **结构重构**：后端包 `app` → `backend`，按组件分子包，agent、worker、repository 各成目录，config 独立目录统一读取 env / `.env`；**仅动结构**，行为与数据结构不变。import、测试、CLI、容器启动命令、文档引用同步迁移。具体目标树属 plan 范畴，不在本 spec 锁定。
- **nginx 形态**：唯一对外入口；前端 dist 由前端构建阶段产出并打进 nginx 镜像；nginx 负责静态 + SPA 回退 + `/api` 反代；后端容器不再托管静态文件；`docker compose` 单命令启动不变；本版 http。
- **配置与密钥**：一切参数经 env / `.env` 注入；`.env` 不入库；代码与镜像不含真实密钥；无密钥时的默认行为必须是"显式降级或阻止启动"二选一，绝无静默假健康。
- **验证分工**：`tests/` 下的自动化测试是开发期正确性附带产物（沿用 000"只测外部行为、端到端接缝唯一"），**不是上线测试**；上线验收由我本人手动执行。真实 provider 的兼容性在开发期以一次真实密钥冒烟验证（见 Testing Decisions），不写入常驻套件、不提交密钥。交付判定按 `## Acceptance Checklist`。

## Testing Decisions

- **原则（沿用 000）**：只测用户可见的外部行为，组件不暴露内部测试接口；测试接缝唯一且为端到端（身份 / 发消息 / 历史 → 回复就绪）。本版无新增产品功能，**不新增接缝**。
- **开发期验证手段（我提交前的自测）**：
  1. **行为回归**：既有 E2E（真实容器 mysql / qdrant / redis + uvicorn 子进程 + chat/search 桩 + 离线嵌入）作为结构重构的回归证明——重构后全量绿，即证明对外行为不变。
  2. **真实 provider 冒烟**：开发中用真实密钥一次性验证 chat（函数调用解析真实输出）、embed（维度探测 / 批量 / 长文本截断）、search（真实响应解析）三家适配层的真实协议兼容——证明 Acceptance Checklist 中 ⭐ 项的真实可用性，**不写入常驻套件、不提交密钥**。
  3. **工程项自测**：对可自动化的部分（启动校验、幂等建表、知识摄入）补开发期检查；纯手动项按 `## Acceptance Checklist` 执行。
- **先例**：`tests/` 下的 E2E 桩套件是开发期正确性的先例基线（真实容器 + uvicorn 子进程 + 协议桩）；真实 provider 冒烟与手动验收无先例，自本版起。

## Out of Scope

- 新增产品功能（撤回 / 流式 / 长期记忆 / 运营端知识管理 UI 等，沿 000）。
- 表结构变更与数据迁移；版本化迁移工具 / `schema_migrations`。
- https / TLS / 证书 / 域名（本版 http；nginx 中可预留注释样板，但不承诺启用）。
- 客户化交付产物：部署 runbook、面向客户的启动 / 运维文档、README（仓库不设）。
- 把"上线测试"自动化。
- 沿 000 的演进项：MQ / outbox 异步投递、多 worker 进程、进程间 RPC、Redis 分布式锁、长期记忆、metrics 中心与完整 errors 分类治理（均见 000 plan 演进接缝）。
